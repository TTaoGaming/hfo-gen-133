# Gmail phase 3 invalid page-token failure probe

## Direct receipt

One bounded `Gmail.search_email_ids` call used:

- one synthetic exact `rfc822msgid:` query expected to be empty;
- `max_results=1`;
- one deliberately invalid, non-secret page-token value;
- no message hydration, retry, fallback, or Gmail mutation.

The connector returned a structured error:

- type: `google_api_error`
- code: `invalidArgument`
- status: `INVALID_ARGUMENT`
- reason: `invalidArgument`
- message: `Failed to search email ids`
- `is_error=true`
- message IDs, headers, bodies, snippets, thread IDs, and page tokens returned: none

The invalid token value and synthetic Message-ID value are intentionally omitted from durable logs.

## Admitted interpretation

`CONNECTOR_REJECTED_THE_FAILURE_PROBE_AS_INVALID_ARGUMENT_WITHOUT_RETURNING_MAILBOX_CONTENT`.

This does not prove that Gmail itself received the request, that the page token was the rejected field, that the query and limit were forwarded unchanged, that the wrapper did not reject locally, or that the result maps one-to-one to raw Gmail HTTP 400 behavior.

## Official contract baseline

Google documents `users.messages.list` as accepting `maxResults`, `pageToken`, and `q`; `pageToken` is defined as a token used to retrieve a specific page. A successful list response contains IDs and thread IDs, an optional next-page token, and a result-size estimate. Google also documents two-layer Gmail API error telemetry: HTTP status and headers plus a JSON error object. A 400 response denotes a client-side request error, including invalid supplied values or combinations. Official `messages.list` quota cost is currently five units per request, but this connector did not expose whether an upstream request occurred or whether quota was consumed.

- https://developers.google.com/workspace/gmail/api/guides/handle-errors

## Gates added

1. Treat `invalidArgument` as a client-argument failure class, not proof of a page-token-specific provider rejection.
2. Never retry invalid-argument failures automatically.
3. Bind a continuation token only to the immediately preceding identical query, labels, identity, and limit.
4. Do not persist mailbox continuation tokens unless a named consumer requires it and storage is approved.
5. Require raw provider telemetry before claiming exact failure parity, quota usage, or retry safety.
6. Keep adoption and fitness credit at zero until a named consumer acknowledges value and operator time is measured.
